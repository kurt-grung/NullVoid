# NullVoid ML Model

Train and serve an XGBoost model for dependency confusion threat scoring. Supports calibration, explainability, batch scoring, and model versioning.

**Python:** 3.9+ is supported. GitHub Actions uses **3.11** for the ML train/eval step—use 3.11+ locally if you want the same `scikit-learn` resolution as CI.

## Model artifacts

Models are stored as JSON, never pickle (a pickled model executes arbitrary code when loaded):

| File | Contents |
| --- | --- |
| `model.model.json` / `behavioral.model.json` | XGBoost booster, native JSON format |
| `model.calib.json` / `behavioral.calib.json` | Platt-scaling parameters `a`, `b` and the feature key order |
| `metadata.json` / `behavioral-metadata.json` | training details plus `artifacts.sha256` for both files above |
| `ensemble.model.json` + `ensemble-metadata.json` | logistic-regression stacker coefficients (optional) |

`model_io.load_model` verifies the sha256 of each file against its metadata and raises `ModelIntegrityError` on mismatch or when metadata carries no hashes; `serve.py` exits 2 rather than serving an unverified model. `*.pkl` is git-ignored.

## Quick Start

From the **project root**:

```bash
# 1. Install Python deps (one-time)
cd ml-model && pip3 install -r requirements.txt && cd ..

# 2. Export features (optional; train.jsonl may already exist)
nullvoid export --out train.jsonl

# Or export known-bad packages from GitHub Security Advisories:
node ml-model/export-features.js --from-ghsa --limit 100 --out ml-model/train.jsonl

# Or export from malware projects you've scanned (appends packages with threats as label 1):
nullvoid scan /path/to/malware-projects --train

# For balanced training, also export clean packages (label 0):
nullvoid scan . --export-training ml-model/train.jsonl --export-training-good ml-model/train.jsonl

# 3. Train the model
nullvoid train --input train.jsonl --output-dir .

# 4. (Optional) Evaluate metrics on train.jsonl with the saved model
npm run ml:eval

# Behavioral model (same idea):
nullvoid export-behavioral --out train-behavioral.jsonl
nullvoid train-behavioral --input train-behavioral.jsonl
npm run ml:eval-behavioral

# 5. Start the ML server (keep running)
nullvoid serve --port 8000
```

Legacy npm aliases are still available for compatibility (`npm run ml:export`, `npm run ml:train`, etc.).

Or run from `ml-model/` directly:

```bash
cd ml-model
pip3 install -r requirements.txt
node export-features.js --from-ghsa --out train.jsonl
node export-features.js --good lodash,react --out train.jsonl
python3 train.py --input train.jsonl --balance --calibrate
python3 serve.py --port 8000
```

### Configure NullVoid

Set `ML_MODEL_URL` in `.nullvoidrc` or environment:

```json
{
  "DEPENDENCY_CONFUSION_CONFIG": {
    "ML_DETECTION": {
      "ML_MODEL_URL": "http://localhost:8000/score",
      "BEHAVIORAL_MODEL_URL": "http://localhost:8000/behavioral-score",
      "ML_EXPLAIN": true
    }
  }
}
```

Start the server with both weights loaded:

```bash
python3 serve.py --port 8000 --behavioral-model-dir .
```

## Training data and labels

Labels are **ground truth only**:

| Label | Source | File |
| --- | --- | --- |
| 1 malicious | GitHub Security Advisories of type **malware** (ecosystem npm). Vulnerability advisories (`type=reviewed`) are *not* malware and are excluded. | fetched at export time (`--from-ghsa`), cached with `--ghsa-cache` |
| 0 benign | Popular npm packages (≥ 100k downloads/month, no malware advisory), generated by `fetch-top-packages.js` and reviewed in the diff | `benign-packages.txt` (~3,500 names) |

The scanner's own verdicts are never labels. Rows written by `nullvoid scan --export-training*` carry `source: scanner-*` and `train.py` drops them unless `--allow-scanner-labels` is passed.

Every row records `name`, `time` (first real publish), `reference` (advisory date for malware, otherwise now), `source` and `advisory`, so the set is auditable and `train.py` can hold out by time.

### What the dependency model can and cannot learn

Once npm takes a malicious package down, the registry serves a *security holding package*: description, maintainers, repository and README are replaced; only the version timestamps in `time` survive. The dependency model therefore uses **publish-history features only** (`publishHistory.ts`: version count, publish span, first-to-second-version gap, cadence, age at reference, name length/entropy/digit ratio/separators) plus the name-pattern features — anything else would teach the model to recognise the placeholder.

Two consequences, both deliberate:

- **Compromised existing packages are out of scope.** About two thirds of recent malware advisories are legitimate packages whose maintainer account was hijacked years after the first release; their publish history is benign by construction. `export-features.js --max-malware-age-days 180` (default) drops them and reports the count. Catching those is the scanner's job (lifecycle/structural/capability analysis), not registry metadata's.
- **Benign packages are also sampled young.** Every malware row is a package caught days after publish. To stop the model learning "new package ⇒ malware", each benign package also contributes early-life snapshots (`--snapshot-ages 2,10,30`): its features as they were 2, 10 and 30 days after first publish. Snapshots stay on the same side of the held-out split as their package.

### Behavioral model

The behavioral model describes a manifest (scripts, dependency counts, lifecycle-script rule hits from `lifecycleScriptAnalysis.ts`). Holding packages have no scripts, so only advisories whose manifest is still on the registry contribute positives (`heldByNpm` is reported). The positive class is small (≈130 manifests); treat its scores as weak evidence — this is why ML threats stay behind `--ml`.

### Held-out evaluation

`train.py` and `train-behavioral.py` hold out the **newest 20 % of packages per class by first publish date** (time-stratified; snapshots travel with their package), score that split, write the metrics to `metadata.json` (`metrics`, `split`, `dataset`), then refit on all rows for the shipped booster (`refit_on_all_rows: true`). `check_metrics.py` fails CI when metrics are empty, below the floors, or regressed more than 5 points of ROC-AUC / PR-AUC against the committed model.

Current committed metrics (see `metadata.json` / `behavioral-metadata.json`): dependency ROC-AUC ≈ 0.98, PR-AUC ≈ 0.69, recall 1.0 at precision 0.66; behavioral ROC-AUC ≈ 0.83, PR-AUC ≈ 0.54.

```bash
npm run build                                         # exporters share the scanner's feature builders
node ml-model/fetch-top-packages.js --out ml-model/benign-packages.txt --min 1500   # refresh benign list (optional)
GITHUB_TOKEN=... node ml-model/export-features.js --overwrite --from-ghsa --limit 5000 \
  --good-file ml-model/benign-packages.txt --out ml-model/train.jsonl
GITHUB_TOKEN=... node ml-model/export-behavioral-features.js --overwrite --from-ghsa --limit 5000 \
  --good-file ml-model/benign-packages.txt --out ml-model/train-behavioral.jsonl
cd ml-model
python3 train.py --input train.jsonl --output-dir . --balance --calibrate
python3 train-behavioral.py --input train-behavioral.jsonl --output-dir . --balance --calibrate
python3 check_metrics.py --metadata metadata.json --min-roc-auc 0.9 --min-pr-auc 0.5
```

## Behavioral training data

Behavioral features are built from the **package manifest** (`ts/src/lib/behavioralFeatures.ts`: scripts block, dependency counts, regex signals, lifecycle-script rule hits) — the same code the scanner runs. Labels:

- **0 (benign)**: `--good-file benign-packages.txt` (or `--good pkg1,pkg2`).
- **1 (malicious)**: `--from-ghsa` (GHSA **malware** advisories; packages already replaced by npm's holding package are skipped) and/or `--bad pkg1,pkg2`.

By default the exporter **merges** into the output file; use **`--overwrite`** for a clean file (CI does).

```bash
npm run build
node ml-model/export-behavioral-features.js --overwrite --from-ghsa --limit 5000 \
  --good-file ml-model/benign-packages.txt --out ml-model/train-behavioral.jsonl
python3 ml-model/train-behavioral.py --input ml-model/train-behavioral.jsonl --output-dir ml-model --balance --calibrate
```

The weekly **ML Model Retrain** workflow refreshes both `train.jsonl` and `train-behavioral.jsonl` this way, trains, runs `check_metrics.py` against the committed metadata and commits the new `*.model.json` / `*.calib.json` / metadata only when the gate passes.

## Export Features

Export uses **npm registry metadata** through the same **`buildFeatureVector`** / **`publishHistoryFeatures`** path as the scanner (`npm run build` first; `ts/dist/lib` is required). Rows include `name`, `time`, `reference`, `source` and `exportedAt`.

```bash
# Known-good packages (label 0)
node export-features.js --good lodash,react,express --out train.jsonl

# Known-bad packages (label 1)
node export-features.js --bad package1,package2 --out train.jsonl

# Extra label lists: one package per line, # comments allowed
node export-features.js --good-file ./curated-good.txt --bad-file ./curated-bad.txt --out train.jsonl

# GHSA malware advisories (label 1) + reviewed benign list (label 0); GITHUB_TOKEN raises the API rate limit
GITHUB_TOKEN=ghp_xxx node export-features.js --overwrite --from-ghsa --limit 5000 \
  --good-file benign-packages.txt --out train.jsonl

# Reuse a saved advisory list (written on first use), tune snapshots / malware age filter
node export-features.js --from-ghsa --ghsa-cache .cache/ghsa-malware.json --snapshot-ages 2,10,30 --max-malware-age-days 180 ...
```

### Git-enriched export (`--with-git`)

To match **commit / timeline** features from real scans, clone packages locally and point the exporter at those directories. Without a path, `--with-git` only warns and rows stay npm-only.

- **`--package-root <dir>`** — each package resolves to `<dir>/<scope>/<name>` for scoped names (e.g. `lodash` → `<dir>/lodash`, `@types/node` → `<dir>/@types/node`).
- **`--package-map <file.json>`** — object map `{ "package-name": "/absolute/or/relative/path" }` (overrides `--package-root` when both apply).

```bash
npm run build   # recommended so export uses ts/dist (same code as the scanner)

node export-features.js --good lodash,react --with-git --package-root ~/clones --out train.jsonl

# Example map
echo '{"lodash":"/path/to/lodash-clone","@scope/mypkg":"/path/to/mypkg"}' > paths.json
node export-features.js --good lodash,@scope/mypkg --with-git --package-map paths.json --out train.jsonl
```

**More label sources:** combine `--bad-file` with community-maintained malicious package lists (e.g. OpenSSF malicious-packages CSV converted to one npm name per line). Curate and version those files; dedup with `dedup-train.js` before training.

## Deduplication

When combining data from multiple sources (export-features, scan), deduplicate before training:

```bash
npm run ml:dedup
# or: node ml-model/dedup-train.js [input.jsonl] [output.jsonl]
```

The same script works for behavioral JSONL (used after `--overwrite` exports in CI).

## Offline evaluation and held-out validation

**Held-out metrics are produced by training itself**: `train.py` / `train-behavioral.py` hold out the newest 20 % of packages per class (`--test-size`), print and record precision, recall, F1, ROC-AUC, PR-AUC and Brier score in the metadata, then refit on all rows. Gate on them with:

```bash
cd ml-model
python3 train.py --input train.jsonl --output-dir /tmp/m --balance --calibrate
python3 check_metrics.py --metadata /tmp/m/metadata.json --min-roc-auc 0.9 --min-pr-auc 0.5 --min-recall 0.8
python3 check_metrics.py --metadata /tmp/m/metadata.json --baseline metadata.json --max-regression 0.05   # vs committed model
```

**In-sample** check of a saved model on any JSONL (optimistic — the model has seen these rows):

```bash
cd ml-model && python3 evaluate.py --input train.jsonl --model . --json
cd ml-model && python3 evaluate.py --behavioral --input train-behavioral.jsonl --model . --json
```

`split_train_val.py` is still available for a manual split (e.g. to score a model on rows exported later): `--time-val-newest --time-field time` puts the newest first-publish dates in the validation set.

On every push to `main`, **Tests** trains both models from the committed JSONL, runs `check_metrics.py` and uploads **`ml-eval-report.json`**. The weekly retrain additionally compares against the committed metadata and refuses to push a regression.

## Training Options

```bash
python train.py --input train.jsonl --output-dir .
python train.py --input train.jsonl --balance          # Oversample minority class
python train.py --input train.jsonl --balance-class-weight  # Imbalance via XGBoost scale_pos_weight only (no oversampling)
python train.py --input train.jsonl --no-calibrate    # Skip Platt scaling
python train.py --input train.jsonl --output-dir models/v1  # Save to directory
```

Use **only one** of `--balance` or `--balance-class-weight`. After oversampling, `scale_pos_weight` is derived from the **post-balance** class counts (≈1.0 when classes match), which avoids double-weighting the minority class.

**Pinned XGBoost hyperparameters** live in `train.py` / `train-behavioral.py` as `XGBOOST_PARAMS` (`n_estimators`, `max_depth`, `learning_rate`, `subsample`, `colsample_bytree`, `min_child_weight`, …). The values used for a run are also written into `metadata.json` / `behavioral-metadata.json` under `xgboost_params` and `scale_pos_weight`.

**CI vs weekly retrain:** The scheduled **ML Model Retrain** workflow trains on the full deduplicated JSONL for maximum data; **Tests** retrains on a held-out split to measure generalization. Both are intentional.

## API Endpoints

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/score` | POST | Score a single feature vector. Add `"explain": true` for reasons and importance |
| `/batch-score` | POST | Score multiple feature vectors. Body: `{"features_list": [...], "explain": false}` |
| `/importance` | GET | Global feature importance from the model |
| `/model-info` | GET | Dependency + behavioral metadata, `feature_schema_version`, manifest `version` from `feature-keys.json` |
| `/explain` | GET | Same as `/importance` |
| `/explain` | POST | Per-sample explanation (SHAP when available) |
| `/health` | GET | Check if model is loaded |

### POST /score

Request:
```json
{"features": {"daysDifference": 30, "scopePrivate": 0, ...}, "explain": false}
```

Response:
```json
{"score": 0.42}
```

With `"explain": true`:
```json
{
  "score": 0.42,
  "reasons": ["timelineAnomaly=0.35: Package created very recently relative to repo history"],
  "importance": {"timelineAnomaly": 0.4, "scopePrivate": 0.15, ...}
}
```

### POST /batch-score

Request:
```json
{"features_list": [{"daysDifference": 30, ...}, {"daysDifference": 365, ...}], "explain": false}
```

Response:
```json
{"scores": [0.42, 0.12]}
```

`/batch-score` rejects requests larger than **`NULLVOID_ML_MAX_BATCH`** items (default **512**). Override the env var to raise the cap.

## Feature manifest and known-good list

- **`feature-keys.json`** — canonical ordered `dependency` and `behavioral` feature names for `train.py`, `train-behavioral.py`, `serve.py`, and `ts/src/lib/mlFeatureKeys.ts`. Bump `version` when you add or reorder columns.
- **`benign-packages.txt`** — the benign class (popular packages, no malware advisory), generated by `fetch-top-packages.js`; used via `--good-file` locally and in the weekly retrain.
- **`training-defaults.json`** — `knownGoodPackages`, a five-package fallback used only when neither `--good` nor `--good-file` is given.

### Extending the dependency feature schema

When you add or reorder columns (e.g. new NLP or code-quality signals in `buildFeatureVector`):

1. Update **`feature-keys.json`**: append or reorder keys and increment **`version`**.
2. **`ts/src/lib/mlFeatureKeys.ts`** imports that manifest at compile time—no manual list to edit unless you change how it is loaded.
3. Update **`export-features.js`** and **`ts/src/lib/mlDetection.ts`** (`buildFeatureVector`) so training rows and the scanner expose every key.
4. Run **`npm run test:ts`** and ensure **`ts/test/unit/ml-feature-parity.test.ts`** passes.
5. Retrain and bump the committed **`model.model.json`** / metadata when you ship the new schema.
## Feature Schema

Features match `buildFeatureVector` output from `ts/src/lib/mlDetection.ts`:

- `daysDifference`, `recentCommitCount`, `scopePrivate`, `suspiciousPatternsCount`
- `timelineAnomaly`, `registryIsNpm`
- `authorCount`, `totalCommitCount`, `dominantAuthorShare`, `commitPatternAnomaly`
- `nlpSecurityScore`, `crossPackageAnomaly`, `behavioralAnomaly`
- `reviewSecurityScore`, `popularityScore`, `trustScore`
- publish history (schema v2, `publishHistory.ts`): `versionCount`, `publishSpanDays`, `firstToSecondVersionHours`, `versionsPerWeek`, `ageAtReferenceDays`, `nameLength`, `nameEntropy`, `nameDigitRatio`, `nameSeparatorCount`

Behavioral (`behavioralFeatures.ts`): script counts/lengths, regex signal counts, dependency counts, `lifecycleThreatScore`, `lifecycleThreatCount`.

## Requirements

- **macOS**: XGBoost requires OpenMP. Run `brew install libomp` if you see `Library not loaded: libomp.dylib`.

## Optional: SHAP

For TreeExplainer-based per-sample explanations on `POST /explain`, install optional deps on the **same environment that runs `serve.py`**:

```bash
pip install -r ml-model/requirements-optional.txt
```

SHAP adds a large dependency; the server still starts without it and uses feature-importance fallback. **`GET /health`** includes **`"shap": true|false`** so clients (e.g. the dashboard via `ML_SERVICE_URL`) can show whether the deployed scorer has SHAP enabled.
